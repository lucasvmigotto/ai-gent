# ai-gent: Codex parity and lifecycle audit

Date: 2026-11-17. Historical audit of main at `0cca79b`, before implementation.

The owner subsequently authorized documenting this analysis and starting development. Read `README.md` and `handoff.md` in this directory for current implementation scope, ownership, and results. Findings below describe the audited baseline; they are not claims that every issue remains unfixed.

## Executive assessment

ai-gent has a substantial, useful engineering workflow core. Its artifact contracts, evidence labels, isolated worktrees, audited runners, and requirement to verify delegated work are worth preserving. Codex can use much of that core today.

Its current Codex integration is nevertheless much closer to skill availability and supervised worker support than to a complete Codex development environment. The distinction is structural: Claude is a privileged coordinator in the skill text, the scheduler's types, review identity, history readers, accounting, and UI lifecycle. Translating tool names will not resolve those differences.

The right direction is a common workflow and policy core with explicit host adapters. Any supported coordinator should be able to plan, build, delegate, review, recover, and land authorized work. Claude-specific panes remain useful clients of that core. Codex should have equivalent access to state and controls through supported native tools, hooks, and command output; identical chrome is unnecessary.

The highest priorities are correctness of task completion and dependency admission; realistic Codex enforcement; independent Codex review; policy enforcement at dispatch; and honest, measured compatibility claims. A second complete pipeline written for Codex would multiply the existing drift problem.

- Current remote `develop`, read through GitHub: `0a61fc4546491d6696fa46a1f2595958f4903ed0`, 18 commits ahead of local main. SSH fetch was unavailable; GitHub API reads succeeded. Compared changed paths and inspected the relevant delegation patches.
- Already addressed on develop: the integration branch rename and the addition of `develop` to review-base selection; Workers and Worktrees pane improvements. These are not proposed again as new work. Develop also adds specs 044 and 045 and repository board work.
- Ran nine small behavioral probes against the installed binary, entirely using synthetic data and temporary directories: five scheduling/source probes and four guard-event probes. No model runs, paid evals, database access, container operations, or remote writes. No actual credential or autonomy file was created or edited.

- Did not run the full build or `scripts/check.sh`: no repository changes or commits were made. Existing test evidence is identified separately from tests run for this audit.

## What should be retained

1. **Artifact ownership and traceability.** `shared/pipeline.md` and its digest define recognizable inputs, outputs, owners, and status gates. This is much more useful than unrelated prompt recipes.
2. **Evidence discipline.** Observed, Inferred, Assumed, Implemented, and Verified have different meanings. Preserving those distinctions reduces confident fabrication and premature completion.
3. **Runner boundaries.** Secrets, repository operations, and database operations have dedicated interfaces. Keep policy in those interfaces where possible, rather than relying exclusively on model obedience.
4. **Verification outside the builder.** Real checks plus independent review are a sound defense against plausible but incomplete implementation.
5. **Worktree and resource ownership.** Project labels, explicit cleanup, dependency-aware landing, and no global pruning protect other work.
6. **Candid trial records.** Spec 041 documents failed assumptions and missing measurements instead of presenting all delegated output as a success. That record is a useful basis for improvement.
7. **Parity fixtures and deterministic packaging.** They provide a practical path for evolving the runtime while retaining behavior.

## Findings and correction plans

### F01 — High: coordinator identity is hard-coded to Claude

Evidence: `plugins/agents/skills/delegate/SKILL.md:8`, `:49`, `:97`; `rust/crates/ai-gent-core/src/delegate/schedule.rs:82`, `:293`.

The skill reserves planning, decisions, review, and landing for Claude and limits Codex to simple bounded tasks. The scheduler encodes `Worker::Claude`; a judgment task falls back to Claude even when the only allowed delegate is Codex. This is observable runtime behavior, not just an unfortunate example.

This was an intentional original scope decision, not merely an implementation accident: spec 041 FR-004a records the owner's November 2 preference for Claude on Rust and judgment-heavy work. The implementation largely follows that requirement. The requirement itself now needs revisiting to meet the broader goal expressed in this audit request. The recorded mixed-agent trials do not establish a controlled general ranking of the providers.

Probe: a `kind: rust` task on `src/lib.rs`, planned with `--allow-agent codex`, returned `worker: claude` and exit 0.

Correction: separate the coordinator role from the agent product. Use a coordinator identity resolved from the active session or explicit configuration, and workers selected by task capability, risk, authorization, available tools, and measured performance. Rust is a language, not a universal proxy for risk. Preserve additional review requirements for authorization/redaction code regardless of which model builds it.

Acceptance: a Codex-only setup can plan and complete both ordinary code and Rust work without requiring Claude; a Claude-led setup retains its current supported workflow; risky work receives the same controls on either host.

### F02 — High: an unsuccessful deliverable can satisfy dependencies

Evidence: `rust/crates/ai-gent/src/cmd/delegate.rs:715` (`claimed_and_done`) and `:739` (`idle_reason`).

Every status with execution state `done` contributes its task IDs to the completed set. Neither supervisor verdict nor integration is required. The role is not filtered, so reviewer tracks can also contribute IDs. This contradicts the continuation contract that dependencies must have landed and that a worker exit is not accepted work.

Probe: T001 was `done` with verdict `rejected` and reason `path-outside-allowed`; T002 depended on it. `delegate idle` returned `ready_tasks: 1`, `reason: dispatch`.

Correction: retain execution state separately from deliverable state. Suggested deliverable progression: queued → building → checking → reviewing → accepted → integrated, with rejected/blocked states. Define a dependency's required state explicitly; for cross-track work consumed from the integration branch, require integrated. Tie checks and reviews to a revision/tree identity. Reviewer completion must never complete the builder's task implicitly.

Acceptance: done-but-pending, rejected, failed, reviewer-only, and accepted-but-not-integrated predecessors do not unlock dependencies that require integration. Changes after review invalidate the prior review evidence.

### F03 — High: dependency planning does not validate or order a DAG

Evidence: `rust/crates/ai-gent-core/src/delegate/schedule.rs:237`.

Dependency-connected tasks are unioned into one track. The track preserves input order, without topological sorting or cycle rejection. In addition to correctness problems, joining every dependent task sacrifices parallelism in fork/join workflows even when ownership permits concurrent work.

Probes: T002 depending on T001, listed first, produced a track ordered `[T002, T001]`. A mutual T001/T002 dependency returned a successful plan rather than a cycle error.

Correction: validate a directed graph, reject self-dependencies and cycles with an explanatory path, topologically order runnable work, and distinguish ownership conflicts from dependency edges. Tracks can remain single-owner execution units without collapsing the entire dependency graph.

Acceptance: shuffled inputs produce valid stable order; cycles and self-dependencies fail; independent branches of a graph can run together and join only after prerequisites satisfy the required acceptance state.

### F04 — High: the Codex guard bridge requires event and decision translation

Evidence: `specs/039-release-3-contract/contracts/tier-policy.md:37`; `rust/crates/ai-gent-core/src/guard/mod.rs:31`; `guard/event.rs:143`; `guard/rules/db.rs:40`; `guard/rules/git.rs:180`.

The project already knows that Codex supports hooks. Its spec records 216 synthetic shell-event matches, but explicitly leaves live firing, trust, ask semantics, and non-shell coverage unresolved. That is useful evidence, not completed integration.

Current Codex documentation states that `PreToolUse` can deny supported calls, but `permissionDecision: ask` is unsupported and the failed hook does not block the call. The existing evaluator uses ask as its fallback on internal failure. Passing that output through unchanged would lose an important part of ai-gent's policy.

There is also a concrete input mismatch. Codex patches carry patch text in `tool_input.command`; the non-shell checks inspect path-shaped fields such as `file_path`. Merely adding an `apply_patch` matcher is insufficient.

Synthetic probes, without executing any edit:

| Event | Credential target | Autonomy target |
|---|---|---|
| Claude-style `Edit` with `file_path` | deny | deny |
| Codex-style `apply_patch` with patch text in `command` | no decision | no decision |

Correction: normalize supported host events into a common operation representation: shell, read, write, patch add/update/delete/move, and structured external calls where policy can be evaluated. Decode affected paths before policy evaluation. Translate ask to a stop that explains the required approval flow; do not replace approval with allow plus a warning. Keep grants narrow and auditable. Distinguish hook controls from the OS sandbox, runner restrictions, branch protection, and remote authorization.

Handle hook trust explicitly in installation and doctor output. A wrapper can turn evaluator failures into deny while the wrapper itself is functioning; it cannot guarantee fail-closed behavior if the host fails to start or times out the whole hook. Report that limitation honestly.

Acceptance: versioned Codex-shaped fixtures, then a live trusted-hook smoke run with harmless allowed and blocked operations; patch moves/deletes, multiline input, nested tool calls, hook errors/timeouts, and stdin continuation are considered. No enforcement claim extends to unsupported or unobserved tool paths.

### F05 — High: dispatch policy and admission are coordinator conventions

Evidence: delegate skill `:146`; `rust/crates/ai-gent/src/cmd/delegate.rs:1099`; `delegate/adapter.rs:217`.

No subcommand reads `.ai-gent/delegate.yaml`. `run` does not require an approved plan, perform pool admission, or call ready/preflight as a dispatch gate. It receives a brief string rather than a validated immutable task policy. The same-track check is a read of status/PID files, not an atomic reservation before process creation. These choices are workable for a careful operator but weaker than a reusable autonomous supervisor should promise.

Correction: load one versioned policy for plan, run, review, and recovery. Reserve a slot under a lock before spawning; reject disallowed workers, duplicate claims, worktree mismatches, and conflicting ownership. Record the decision and policy revision. Keep an explicit operator override where justified, with clear provenance, rather than invisible bypass paths.

Acceptance: opt-out is respected by the executable; two simultaneous dispatch attempts cannot claim the same slot or track; dispatch without required approval is rejected before a model starts. Distinguish process capacity, worktree/build storage, and model/quota limits.

### F06 — High: independent review is confused with agent brand

Evidence: `rust/crates/ai-gent-core/src/delegate/review.rs:12`, `:122`; `delegate/status.rs`.

Codex cannot review a Codex track, even in a fresh session. Claude is distinguished by profile directory and OpenCode by model. The installed Codex CLI exposes profiles, so the statement that Codex has no profile is also outdated. More fundamentally, an account/profile boundary is not the same thing as independent reasoning context.

Status does not retain enough immutable identity to reconstruct all these distinctions reliably after restart: model, profile/config identity, builder session/thread, and the reviewed revision are missing.

Correction: record builder session/run identity, provider/agent, model, configuration identity without secrets, worktree, task, and revision. Allow same-provider review in a fresh context for ordinary work. Make different-model/provider review a configurable higher-assurance requirement, not a hard dependency on owning a second vendor account. Reviewers receive requirements, diff, and test evidence, not the builder's argument for why its work is good.

Codex native subagents inherit parent permissions; a custom reviewer instruction is not a separate read-only sandbox. Use an independently constrained execution path when enforced read-only review is part of the promise.

Acceptance: a Codex-only user can complete independent review; the builder session cannot certify itself; review results identify the exact material reviewed and whether coverage was complete or truncated.

### F07 — Medium/High: the Codex adapter relies on ambient configuration

Evidence: `delegate/codex.rs:66`, `:126`, `:180`, `:202`; `delegate/adapter.rs:49`; installed `codex exec --help`.

Model selection on `delegate run --model` applies to OpenCode, not Codex. RunRequest has no model/effort/profile policy. The Codex launcher passes sandbox flags but does not pin or report all effective capabilities; preflight says network is absent while explicitly noting it was not probed. It leaves `env_remove` empty, whereas isolation work elsewhere already recognized the risk of inherited Git location variables.

The extra writable temp directory is the ambient TMPDIR or system temp, rather than a private per-run directory. The prompt is a command-line argument. Builder briefs do not share the review prompt's platform-specific size cap.

Correction: make agent configuration explicit and versioned: model, supported reasoning effort, profile, sandbox/network settings, approval behavior, enabled extensions/tools, worktree and scratch locations. Validate requested settings against host support and managed policy; never silently weaken it. Remove stale Git location variables, allocate a unique scratch directory, and report effective rather than assumed restrictions. Supply the prompt through a bounded stdin path supported by `codex exec` and close it after the brief, addressing argument-length and process-list exposure without reopening the old stdin hang.

Do not copy login secrets into a generated profile. Keep authentication in its authorized host mechanism.

Acceptance: explicit model/effort selection, deterministic launch tests, incompatible-config refusal, inherited-Git-variable tests, private scratch, and large briefs on Windows and Unix. Preflight reports unverified capability restrictions instead of promising them.

### F08 — Medium: continuation has a Claude-specific wake-up mechanism

Evidence: `shared/worker-continuation.md`; delegate and orchestrate skills; `delegate/watch.rs`; `delegate/events.rs`.

The durable event log and per-event acknowledgment are good foundations. A Claude Monitor waking an idle coordinator is not a portable contract. The model cannot assume that a process writing a file or a UI toast starts a new Codex turn.

Correction: define continuation modes per host. Native subagents use native completion notifications; detached workers use the durable protocol plus a supported host watcher or bounded wait/reconcile loop. If autonomous wake-up is unavailable, report that and preserve a recoverable checkpoint. Avoid tiny repeated polling turns. `SubagentStop` hooks may help registration and observation, but availability and coverage must be tested before they become the sole lifecycle mechanism.

Use unique run IDs rather than epoch seconds as run identity: reruns of the same track within one second can otherwise reuse `track:started:state`. Preserve ack/replay behavior across migration. Bound event log growth, reads, and subprocess waits; snapshot git calls have timeouts, but the general delegation git helper uses unbounded `Command::output`.

Acceptance: restart, compaction, crash, duplicate and stale event, same-second rerun, quota hold, and finished-reviewer events recover without duplicate landing or lost work.

### F09 — Medium: Codex history and checkpoint identity are missing

Evidence: `plugins/project/scripts/sessions.py:290`, `:329`; `plugins/project/scripts/checkpoint.py:68`.

The recap reader supports Claude and OpenCode only. Checkpoint stamps identify the tool as OpenCode if its environment marker exists, otherwise Claude. Consequently a Codex-written checkpoint can be mislabeled, and a later recap misses Codex's own previous work.

Correction: introduce a session-source adapter with explicit host/session identity and a normalized digest. Add a versioned, fixture-tested Codex history reader or supported export integration. Treat transcript storage as an evolving format, not a permanent public API. Prefer checkpoints as the durable intent record; use transcripts as supporting evidence and never as new authorization. Distinguish permissions that persist within a session from an old handoff's proposed next actions.

Acceptance: a Codex session writes the correct identity; a later Codex or Claude recap finds it, includes compaction/interruption state, excludes the active session, handles linked worktrees, and redacts synthetic secrets.

### F10 — Medium: usage accounting cannot support Codex-led planning

Evidence: `shared/token-tracking.md`; `plugins/agents/scripts/token_report.py`; `delegate/status.rs`; `delegate/watch.rs`.

The main reporting path is Claude-transcript based, while detached Codex runs contribute a smaller set of final usage fields. A Codex coordinator and its native subagents are not a first-class accounting source. Generic worker labels and missing model/run identities limit comparison and deduplication.

Correction: define a normalized usage event: run and parent IDs, agent, model, input, cached input, output, reasoning subset, timestamps, source, and availability/confidence. Distinguish unknown from zero, API-equivalent cost from actual subscription expenditure, and token totals from account rate-limit windows. Avoid double-counting provider totals and child runs. Preserve provider-specific fields and unavailable states rather than inventing equivalence.

Keep measured Claude heuristics in a Claude profile. Rules about five-minute caches, 150k compaction, 40-call cards, and Sonnet/Opus economics do not become Codex facts by moving them into a shared reference.

Acceptance: Codex-only coordinator, native children, and detached workers receive correct deduplicated attribution; missing usage remains unknown; a fallback budget does not claim to know the account quota.

### F11 — Medium: source term matching is presented as confirmation

Evidence: `delegate/sources.rs:8`, `:160`, `:191`; CLI `delegate.rs:651`.

The implementation explicitly cannot distinguish a claim from its negation. Its enum nevertheless calls a complete lexical match `Confirmed`, and the CLI returns success. That makes a screening helper easy to misuse as a verification gate.

Probe: claim `crate-x is archived`; source `crate-x is not archived.` Result: `outcome: confirmed`, exit 0. Only the identifier `crate-x` was extracted, so even the critical predicate was not checked.

Correction: rename the result to `terms-present` or `lexical-match` and state that semantic support remains unverified. Return structured excerpts for a reviewer to accept/reject/mark uncertain, preserving claim-to-source mapping. Do not claim that adding a few negation patterns solves general semantic entailment. Bound local reads and require ordinary permitted files; a byte cap alone does not bound opening/reading a FIFO.

Acceptance: a negated or unrelated passage never yields a semantic confirmation; verdict-changing claims require explicit evidence assessment.

### F12 — Medium: installation support is not behavior support

Evidence: `setup.sh:530`; `scripts/test-install.sh:151`; `.github/workflows/check.yml`; `shared/tiers.json`; `specs/041-agent-delegation/tasks.md`.

Generated namespaced entries in `~/.agents/skills` are useful and appropriately avoid colliding short names. They point to canonical source instructions instead of forking the content. Preserve that benefit.

However, the generic stub only says to substitute equivalent tools and load other skills with a skill tool. It does not provide execution semantics for missing tools, model routing, permission gates, asynchronous monitoring, or UI surfaces. The Codex CI case primarily verifies generated files. Rust fake-agent tests prove protocol handling, not a real Codex safety boundary or end-to-end skill behavior.

Current Codex supports plugins and hooks; `codex plugin --help` confirms a plugin surface locally. The README's broad grouping of Codex with agents having no plugin namespaces is therefore no longer a good description of available integration options, although its statement that ai-gent currently installs advisory guards is honest.

Correction: keep a neutral canonical workflow and generate small host-specific launch/capability guidance. Add supported Codex custom role definitions where useful. Offer native plugin packaging as a controlled next step, with a Codex hook manifest separate from Claude's TS modules. Retain stubs as a supported compatibility path and prevent duplicate discovery when a native plugin is installed. Respect trust review and don't overwrite personal config.

Expand the compatibility matrix to capabilities and evidence: installed, loadable, invoked, behavior-tested, enforcement-tested, with host/version/OS. Automate schema and protocol tests; keep paid live runs explicitly budgeted and publish their evidence without making ordinary CI spend user tokens.

Acceptance: an installer test, a real skill-discovery probe, a protocol test, a live behavior run, and a guard test are labeled as different evidence classes.

### F13 — Medium: shared skills contain avoidable workflow mismatches

Evidence: `shared/spec-kit.md`; `project/spec/SKILL.md:42`; `project/pitch/SKILL.md:64`; `qa/e2e/SKILL.md:3`, `:24`; `shared/asking.md`; `delegate/checks.rs`.

- Spec Kit bootstrap always chooses Claude integration and reads `.claude/skills`. The fallback can work by reading files, but it is an explicit host dependency. Add a tested integration selector or neutral entrypoints; pin/test the supported Spec Kit contract before generating flags.
- Pitch selects Canvas from the word Codex, although a CLI session may have no Canvas tool. Choose by available surface, with the existing static HTML/Markdown fallback.
- `qa:e2e` says Playwright by default in its description but selects Selenium for greenfield in the body. Align the description, browser contract, tooling, and examples.
- QA's both-sides Implemented gate needs explicit N/A treatment for CLI-only, library, and frontend-only products.
- The asking contract includes “no answer” as delegated decision authority. Distinguish explicit “you decide/skip” from an unanswered asynchronous question or timeout; missing approval never becomes approval.
- Delegation's main skill commits before review, while its landing reference reviews before committing. Establish one sequence and bind review evidence to the final tree.
- Blanket protected paths refuse every file under `plugins/` and `shared/`, regardless of an exact owner-authorized task. The worker pack already allows such an exception but the brief/check code cannot express it. Support explicit scoped authorization, keeping protected defaults and review requirements.
- The weakened-test check is a heuristic based partly on assertion counts; the environment-prose check rejects words such as “sandbox.” They are useful review signals, not proof of test strength or misbehavior. Permit an audited resolution for legitimate test consolidation and documentation instead of forcing the coordinator to bypass the whole mechanism.

Acceptance: run representative host-specific skill scenarios, including absent optional tools and a non-web application. No skill silently fabricates an unavailable tool or turns missing input into authorization.

### F14 — Medium: status and evidence tables drift from their sources

Evidence: `specs/README.md`; task files for 033, 037, 041 and 043; spec 041 T020 and T022; develop comparison.

Examples at the audited main snapshot: 033's index says 23/40 tasks while its task file has 31 checked and 9 open. 041's index says 21/23 while the file has 23 checked and one open. T022 retains a “no skill calls these yet” gap although current skills explicitly call the events/watch commands. The latest specs 044/045 were added on develop without a change to the main specification index in that comparison.

Correction: generate counts and structural inventories from canonical tasks. Keep completion assertions tied to evidence records and their source revision. Validate feature index coverage and expected links in CI. Do not auto-tick tasks merely because files exist; stale claims need owner review, not optimistic generation.

The release-gates record explicitly documents owner waivers for unavailable platform checks. Preserve them as waivers and disclose them; they are not passes and should not be silently revoked by this audit.

The script inventory falls into six responsibilities: runtime helpers (`wt`, tokens, sessions/checkpoint/repo state, DB/repo/spec runners, compact); installation/update/configuration; guard fixtures/parity/benchmarks; consistency and generation; packaging/release/rollback/publishing; and tests/evals. These responsibilities are already recognizable, but their host assumptions differ. Session/accounting helpers need Codex sources; installer helpers need Codex trust/config handling; guard drivers need Codex operation shapes; evals need a portable scenario layer; packaging must include any new runtime resources. Release and registry publishing should remain shared rather than acquiring provider-specific copies.

The delegation source contains several correct recovery mechanisms, but the public task file is still mainly prose while the executable planner expects separate JSON carrying paths, kinds, needs, and dependencies. That translation is a recurring model task and a drift opportunity. Add validated task metadata or a deterministic export while retaining readable task lists.

### Common runtime with explicit host adapters

Use the existing Rust workspace rather than inventing a separate Codex service or immediately adding a mandatory daemon.

1. **Workflow layer:** artifact ownership, task DAG, acceptance states, authorization, policy, resource reservations, evidence, and run history. Provider-neutral.
2. **Execution layer:** explicit adapters for Codex, Claude, and other supported hosts. Each reports capabilities, limitations, identity, launch settings, events, usage, cancellation, and supported recovery. Native children and detached CLI workers are different execution modes of the same logical task.
3. **Host layer:** Codex skills/custom agents/hooks/plugins; Claude skills/hooks/mods; CLI/JSON views for every core action. Keep optional UI presentation out of the policy engine.

Start with small versioned records. A task needs identity, goal, inputs, outputs/write scope, prerequisites, required capabilities, authorization scope, checks, and reviewer requirements. A run needs a unique ID, task/parent, host/agent/model/config identity, branch/worktree/base revision, lifecycle state, usage availability, and artifact references. Acceptance needs the tested/reviewed revision and the decision maker. Do not store prompts or secrets in the public status view.

Markdown remains the human-authoring format where useful; a validated structured representation should drive scheduling. Avoid asking a model to repeatedly reconstruct path ownership, dependencies, and risk from unrelated prose.

## Implementation sequence, separate from the 3.0.0 work

### Broader product improvements

The toolbox covers discovery, design, implementation, testing, delivery, and several maintenance tasks well. To fulfill the broad lifecycle ambition, the next product questions are scale of process and feedback after release.

- Offer explicit lightweight, standard, and higher-assurance workflow profiles. A small application kick-start can use a concise brief, the few consequential architecture decisions, one executable task list, and meaningful verification. Larger systems can expand the same artifacts. Never silently drop important authorization or data requirements to make a profile lighter.
- Make applicability follow the product shape: CLI, library, web app, background worker, desktop/mobile client, and event-driven service need different contracts and evidence. OpenAPI is useful where HTTP operations exist, not a universal software lifecycle seam.
- Add a production-feedback path when the user requests operations support: inspect authorized telemetry, connect a symptom to a release, measure impact, propose rollback or repair with the existing approval boundary, and feed a verified regression back into requirements/tests. Existing security runbooks and DB investigation are useful pieces, but the catalog does not offer a general incident/operational-diagnosis workflow.
- Keep the distinction between personal conventions and portable guarantees explicit. This repository's attribution rules, integration branches, merge-count rule, pass preference, browser/container choices, and release style are owner policy, not universal truths. Provide configured defaults and respect project-specific overrides.
- Measure success as time to a working verified outcome, correction effort, escaped defects, interruption recovery, and total coordinator-plus-worker resource use. Raw output size, tool count, or amount of documentation is not success.

For evaluation, separate portable scenario definitions from host harnesses. Existing trigger graders can explicitly look for a Claude `Skill` tool invocation (`plugins/agents/evals/delegate-to-codex/graders/fires-delegate.md`), which does not transfer to a Codex host lacking that tool. Score the supported invocation route and resulting behavior for each host. Require deterministic artifact/policy checks where possible and record live-agent rubric/model/version and repeated trials where variance matters. The current comparison honestly lacks a controlled direct-work baseline; preserve that caveat before making quality or savings claims.

## What first-class Codex support should prove

- A new Codex-only project can go from a small brief to a working verified feature without Claude installed.
- An existing project can be surveyed, specified incrementally, changed, tested, and documented without inventing irrelevant pipeline artifacts.
- A Codex coordinator can dispatch native children or explicitly configured CLI workers, follow their completion, review independently, and land only authorized work.
- A finished or rejected worker cannot accidentally unlock downstream tasks or forge a verification claim through ordinary status updates.
- Guards block the supported denied operations on a real trusted Codex hook path, including patches, and the docs identify exceptions/failure behavior.
- Interrupted work can be recovered by either Codex or Claude with correct identity, state, blockers, and outstanding permissions.
- Every advertised capability has host/version/OS-specific evidence; unmeasured usage and untested platform behavior remain visibly unknown.
