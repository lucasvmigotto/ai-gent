# dbrun to Rust: spike report (2026-11-01)

Evidence for `specs/038-db-runner-spike/` and decision D26 (`docs/product/rust-decisions.md`).
Produced by a research agent; the prototype and its `golden.json` lived in a scratchpad and are not in the repo. What was **measured** and what was only **read or assumed** is marked. Nothing here is a decision: the owner decides in 038.

## What dbrun does (read from `plugins/db/scripts/dbrun.py`)

- **Host side:** profiles and pass, classification, cost rules, the statement scanner, masking, redaction, the pre-execution log, plans with a tamper check, backups and `script`, all in stdlib Python.
- **Driver side:** a child process, `dbrun.py _exec`, takes JSON on stdin and returns one JSON line. It runs through `uv run --with <pin>` on the host, or in a digest-pinned uv + Python client container that joins the database container's network namespace.
- **Pins:** psycopg 3.3.6, PyMySQL 1.2.3 (mysql and mariadb), pymssql 2.4.4, oracledb 26.0.1 (thin mode, thick as a fallback). SQLite runs in-process.
- **Read-only enforcement:** PostgreSQL `default_transaction_read_only=on`; MySQL and MariaDB a READ ONLY transaction (the timeout variable is picked after `SELECT VERSION()`); Oracle `SET TRANSACTION READ ONLY`; SQLite `mode=ro` plus `query_only`; SQL Server has no server-side read-only mode, so it relies on the classifier and a rollback.
- **Backups:** `pg_dump` and `mysqldump` run inside the database container, `BACKUP DATABASE` goes through a separate autocommit script, Oracle has none. These are already container shell-outs and do not depend on the driver choice.

## Prototype results (measured)

**Safety core.** The scanner, splitter, classifier, `is_ddl`, `catalog_only`, cost rules, masking, Luhn, redaction and `network_args` were ported in about 330 lines of Rust. A golden file generated by running the real Python covers 171 strings across 6 engines (1026 classify verdicts with reason text, 1026 splits, 1026 `is_ddl`, 4104 cost cases, mask with reveal on and off, redact, network): **zero diffs**. The only gaps were regex lookarounds (the Oracle `DBMS_` exclusion and the redaction boundaries), written by hand. Caveat: the goldens are generated from the Python, and cover reads only.

**sqlparser as the classifier.** sqlparser 0.63 disagrees on **163 of 1026 cases, and 119 of those say READ where dbrun says WRITE** (`pg_sleep`, `lo_import`, `dblink_exec`, `GET_LOCK`, `UTL_HTTP`, `WITH (UPDLOCK)`, `EXPLAIN (ANALYZE)`). A parser answers "is this a query", not "does it have side effects". Keep the token scanner and denylist; a parser is at most an extra, stricter layer.

**Engines** (read path and server-side write refusal only; plan, apply and restore were not run):

| Engine | Result | Cold start |
|---|---|---|
| sqlite (rusqlite) | read OK, write refused by the server | 48-65 ms |
| postgresql 17 (NoTls) | read OK, `transaction_read_only=on`, write refused | 88 ms |
| mysql 8.4 | read OK, write refused (ERROR 1792) | 160 ms |
| mariadb 11.4 | read OK, write refused (ERROR 1792), same binary | 57 ms |
| sqlserver 2022 (tiberius-ng + rustls, encryption required, `trust_cert`) | read OK over TLS | 69 ms |
| oracle | **not run** | |

PostgreSQL errors show only "db error" unless `as_db_error()` is used. Python baseline: stdlib start 24 ms; a warm `uv run --with PyMySQL` is 176 ms before connecting.

**Release binary sizes** (x86_64 gnu, opt-level z, LTO, strip; 20-66 s builds): core only 1.56 MB; + sqlite 2.63 MB; + postgresql 2.09 MB; + mysql 1.98 MB; + mssql (rustls) 3.72 MB; sqlite + postgresql + mysql 3.52 MB. All drivers together are an estimate of 5-6 MB (not built). Size is not the constraint; the build toolchain is.

## Engine x route

| Engine | Native driver | Container shell-out | Stay Python |
|---|---|---|---|
| sqlite | **recommended**: S, +1.1 MB, no installs | n/a | n/a |
| postgresql | M, +0.5 MB, needs a TLS choice, risk is type mapping | `psql` in an image: M, loses types | no effort, needs uv |
| mysql, mariadb | M, +0.4 MB, one client for both | CLI parsing: M, weak typing | as above |
| sqlserver | M-L, +2.2 MB, risk is fork health | `sqlcmd` image: M, heavy (assumed) | works today |
| oracle | L and risky (Instant Client, or a beta crate) | `sqlplus` image: M, awkward output | **recommended for now**: S |

## Recommendation: option H (hybrid)

Keep the Python `_exec` helper for engines that are not yet native, and say openly that uv is required for Oracle (and SQL Server until phase 3). Phasing:

1. Rust core and CLI parity, using the Python `_exec` helper for every driver; run `scripts/test-dbrun-engines.py --runner` against the new binary.
2. Native sqlite, then postgresql, then mysql and mariadb.
3. Native SQL Server if tiberius-ng or another crate passes the engines script and the TLS checks on the 2022 image.
4. Oracle: re-evaluate `oracledb` once it leaves beta; otherwise the helper stays.
5. The Windows, aarch64 and musl matrix before shipping any phase.

## Strongest case against porting

The Python logic is audited, tested and works. The zero-diff result came from generated goldens and covered reads only; type mapping, error text, timeouts, TLS defaults and plan/apply semantics were not exercised. Drivers are the hard part and Rust is not ahead: Oracle needs a client library or a beta crate, SQL Server relies on a one-person fork, PostgreSQL TLS needs an extra crate. So "needs neither uv nor Python" stays false for some users, and db users already have containers or uv, so the gain is mostly packaging and startup for a credential-handling path.

Do **not** port if: the owner accepts "db needs uv" long term; the Windows or musl TLS builds prove painful; phase-1 plan/apply/restore parity fails the engines script; or tiberius-ng and `oracledb` both stay unfit, leaving only sqlite, PostgreSQL and MySQL native (then keep the script and document the requirement).
