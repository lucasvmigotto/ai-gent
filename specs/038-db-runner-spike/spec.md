# Feature Specification: Database runner spike (does `dbrun` move to Rust, and how)

**Feature Branch**: `docs/specs-rust-tools` (specification only)

**Created**: 2026-11-01

**Status**: Draft

**Type**: **a time-boxed spike, not a port.** This spec produces a decision, not a binary. It authorises experiments and a written verdict; it does not authorise replacing `dbrun.py`.

**Input**: `docs/product/rust-decisions.md` (D9 lists `db` as "later"; D19 (superseded by D26, which puts the port in 3.x): "`dbrun` is last or never: its drivers come from `uv run --with` or a container, so a Rust port needs native drivers or a container shell-out. A spike decides."), `specs/008-db-runner/` (the behavioural baseline), `plugins/db/scripts/dbrun.py` (1844 lines), `plugins/db/scripts/test_dbrun.py` (647 lines; the suite reports 51 tests, 41 defined, the rest are inherited runs in subclasses), `scripts/test-dbrun-engines.py` (351 lines; real engines, weekly in `.github/workflows/scheduled.yml`), `plugins/db/references/{runner,safety,engines/*}.md`.

**Depends on**: 032 (workspace), 037 (the pass-store module and the repo-runner patterns for secrets, redaction and guards).

## Context and ground rules

- The reason `dbrun` is special [OBSERVED: `driver_process`, lines 1088-1135]: the host process is stdlib Python and does classification, masking, logging, plans and backups; the **database drivers run in a child process** `python dbrun.py _exec`, started with `uv run --no-project --with <pinned driver>` either on the host (remote targets) or inside a **client container** (`CLIENT_IMAGE`, an uv + Python 3.12 image pinned by digest) that joins the local database container's network namespace. Credentials travel only on the child's stdin. SQLite runs in-process with the stdlib.
- Drivers pinned today: `psycopg[binary]==3.3.6` (PostgreSQL), `PyMySQL==1.2.3` (MySQL and MariaDB), `pymssql==2.4.4` (SQL Server), `oracledb==26.0.1` (Oracle, thin mode; thick mode via `AI_GENT_ORACLE_CLIENT_LIB`). Engines in `ENGINES`: postgresql, mysql, mariadb, sqlserver, oracle, sqlite.
- Without `uv` and without a container engine, `dbrun` already fails with an install message (`EXIT_CONNECT` 4). So today the db plugin **requires uv or Podman/Docker**; a plain "install the release package" user without either cannot use it. That is the one place where the premise of the whole Rust effort ("a user installs once and needs neither uv nor Python") is not met.
- The safety logic is the valuable part and must not regress: the statement scanner and classifier, cost rules, masking, redaction, the local proof, plans/apply/restore and the command log. None of it depends on a driver.
- The decision gates other work: if the answer is "not yet", the guards, skills and `check.sh` blocks for db stay as they are and `ai-gent doctor` reports `uv` (or a container engine) as a requirement of the db plugin.

### Findings so far (from `docs/product/dbrun-spike-report.md`)

- **Measured**: the safety core (scanner, splitter, classifier, `is_ddl`, `catalog_only`, cost rules, masking, Luhn, redaction, `network_args`) ported in about 330 lines of Rust with zero diffs against a golden file generated by running the real Python (171 strings, 6 engines: 1026 classify verdicts with reason text, 1026 splits, 1026 `is_ddl`, 4104 cost cases, mask, redact, network). Caveat: the goldens come from the Python and cover reads only. The only gaps were regex lookarounds (the Oracle `DBMS_` exclusion and the redaction boundaries), written by hand.
- **Measured**: `sqlparser` 0.63 as the classifier disagrees on 163 of 1026 cases, and 119 of them say READ where dbrun says WRITE (`pg_sleep`, `lo_import`, `dblink_exec`, `GET_LOCK`, `UTL_HTTP`, `WITH (UPDLOCK)`, `EXPLAIN (ANALYZE)`). It is rejected as the classifier: a parser answers "is this a query", not "does it have side effects". The token scanner and denylist stay; a parser could at most be an extra, stricter layer.
- **Measured**: read plus server-side write refusal on sqlite (rusqlite), PostgreSQL 17, MySQL 8.4, MariaDB 11.4 (one binary for both) and SQL Server 2022 (tiberius-ng with rustls, encryption required, `trust_cert` for the test image; read only). Cold starts 48-160 ms against a Python baseline of 24 ms for stdlib start and about 176 ms for a warm `uv run --with PyMySQL` before connecting.
- **Measured**: release binary sizes (x86_64 gnu, opt-level z, LTO, strip): core only 1.56 MB; + sqlite 2.63 MB; + postgresql 2.09 MB; + mysql 1.98 MB; + mssql (rustls) 3.72 MB; sqlite + postgresql + mysql 3.52 MB; all drivers about 5-6 MB (an estimate, not built). Size is not the constraint; the build toolchain is.
- **Read or assumed, not run**: Oracle (no prototype); plan, apply and restore; the remote-declared checks of the engines script; PostgreSQL and MySQL TLS; musl, aarch64 and Windows builds; the `sqlcmd`, `psql` and CLI container routes.
- **Backups are driver-independent**: `pg_dump` and `mysqldump` already run inside the database container, `BACKUP DATABASE` goes through a separate autocommit script, Oracle has none. They are container shell-outs whatever driver is chosen.
- The prototype and its `golden.json` lived in a scratchpad and are **not in the repo**; E1 regenerates the goldens from the Python with a committed generator.

## User Scenarios & Testing *(mandatory)*

The "users" here are the owner (who decides) and the builder who runs the experiments.

### User Story 1 - A written decision with evidence (Priority: P1)

The owner reads one page, `specs/038-db-runner-spike/decision.md`, that picks one of five options with measured evidence and a recommended release.

**Why this priority**: D19 asks for exactly this; everything else feeds it.

**Independent Test**: `decision.md` exists, follows `contracts/decision-template.md`, every experiment E1-E8 (E6 as E6a and E6b) has a result (pass, fail or not run with a reason), and no section contains "TBD".

**Acceptance Scenarios**:
1. **Given** all experiments ran, **Then** the decision names an option and, for each engine, native / container / stay.
2. **Given** an experiment could not run (no Windows machine, no Oracle image), **Then** it is marked "not run" with the reason, and the decision says what it does not cover.

### User Story 2 - Know what each option costs per engine (Priority: P1)

For each of the six engines the spike records: the Rust driver candidate (or the CLI inside an image), whether it runs without a native library, TLS support, timeout and statement-limit support, how result types map to the JSON the runner emits, and the effort in tasks.

**Independent Test**: `engine-matrix.md` has six rows and no empty cells.

**Acceptance Scenarios**:
1. **Given** PostgreSQL, **Then** the row compares a native Rust client with `psql` in the client image, on the checks of E2.
2. **Given** SQL Server and Oracle, **Then** the row states whether any maintained pure-Rust driver exists today and what it needs (sqlx dropped MSSQL support pending a rewrite and does not list Oracle [RESEARCHED: S3]; the spike report read the dedicated crates: `tiberius` 0.13.0 for SQL Server (maintenance doubts, see Sources) with the fork `tiberius-ng` 0.13.1 as the candidate, and for Oracle the `oracle` crate 0.6.3 (needs Oracle Client libraries on every machine) and `oracledb` 26.0.0-beta.5 (pure Rust thin mode, beta) [RESEARCHED: S8, S9]; E5 and E6 test them).

### User Story 3 - Prove the safety logic is portable first (Priority: P1)

Before any driver question, the classification and masking logic is shown to port with identical results. The report's prototype already reached zero diffs on generated goldens; this story makes that result reproducible in the repo.

**Independent Test**: experiment E1 (the safety core ported as a driver-free Rust library) passes the classifier, cost, mask, redact and network tests as shared fixtures, plus a committed `golden.json` generated from the Python (reason text included).

**Acceptance Scenarios**:
1. **Given** the 8 `ClassifierTest`, 2 `CostTest`, 3 `MaskTest`, 2 `RedactTest` and 1 `NetworkTest` tests, **Then** their cases run as fixtures against the Rust core with identical outputs.
2. **Given** a `golden.json` generated by running the real Python over the 171-string corpus, **Then** the Rust core matches it on classify verdicts and reason text, splits, `is_ddl`, cost cases, mask, redact and network, and the two lookaround gaps (the Oracle `DBMS_` exclusion, the redaction boundaries) are recorded with how each was written by hand.
3. **Given** the engine-specific scanning rules (backslash quoting for MySQL/MariaDB, bracket identifiers for SQL Server, `parse_modes`), **Then** `test_engine_specific` and `test_backslash_trick_refused` pass.

### User Story 4 - A "not yet" answer is a first-class outcome (Priority: P2)

If the verdict is "not yet", the spec lists exactly what stays, what changes (documentation, `doctor`), and when to revisit.

**Independent Test**: the "If the answer is not yet" section of `decision.md` is filled even when another option is chosen (it is the fallback plan).

## Requirements *(mandatory)*

- **FR-001**: The spike answers: (a) can the safety core move to Rust with no behaviour change; (b) which option is right: N (native drivers for all engines), H (hybrid: native for sqlite, PostgreSQL, MySQL and MariaDB; a container client for SQL Server and Oracle), C (container shell-out for every networked engine, native sqlite), S (stay a Python script that needs `uv`), or **H-exec** (H with the Python `_exec` helper retained: the Rust binary owns the safety core, the CLI and sqlite, and drives the existing `dbrun.py _exec` child for every engine that is not yet native; it is the safe first step and needs `uv` openly for Oracle and, until it is proven native, SQL Server); (c) in which release; (d) what the package ships. The report recommends H-exec with the phasing in `plan.md`; that is a recommendation, not a decision.
- **FR-002**: Time box: the spike closes after E1-E8 or after 5 builder sessions, whichever comes first; unfinished experiments are reported as not run.
- **FR-003**: No production code replaces `dbrun.py` during the spike. Prototype code lives under `rust/spikes/dbrun/` (not shipped, excluded from the package allowlist, removed or kept per the decision). Prototypes never connect to a real remote database: only throwaway containers and a temp sqlite file (the `scripts/test-dbrun-engines.py` rule).
- **FR-004**: Any prototype that reads a credential follows `shared/secrets.md`: a throwaway container's fixture password only (the engines script's `Dbrun_Test_1`), never a real credential, never in argv, never printed.
- **FR-005**: Every experiment states its pass/fail rule before it runs, in `contracts/experiments.md`.
- **FR-006**: The verdict uses `contracts/decision-template.md`; the owner's sign-off is a field in it.
- **FR-007**: The engines in `scripts/test-dbrun-engines.py` are the acceptance set for any "yes": postgresql (`docker.io/library/postgres:17`, 512m), mysql (`mysql:8.4`, 1g), mariadb (`mariadb:11.4`, 512m), sqlserver (`mcr.microsoft.com/mssql/server:2022-latest`, 2g), oracle (`gvenzl/oracle-free:23-slim`, 2g). One engine at a time, container and volumes removed before the next, by ID. The script's checks: the local proof, masked and revealed reads, `--explain`, plan then apply then restore (the new table must be gone after the restore), a count-mismatch rollback, the system-database refusal; then the same server as a remote target declared `development`: the read-only refusals and a change script that is never executed.
- **FR-008**: The disk and memory rules of the engines script apply (a free-space warning; peak memory is one engine's cap, at most 2 GB); the spike does not override the disk floor.
- **FR-009**: Behaviour that must not regress is the checklist below; the decision signs off each item.

- **FR-010**: The classifier stays the token scanner plus denylist. `sqlparser` (or any parser) is rejected as the classifier (163 of 1026 disagreements, 119 unsafe); it may be proposed only as an extra, stricter layer, with its own measurement.
- **FR-011**: Every native or process route proves a write is refused **by the server** in read mode, not only by the scanner. Shown so far: sqlite, PostgreSQL, MySQL, MariaDB. SQL Server has no server-side read-only mode today and relies on the classifier and a rollback (stated in the decision, not hidden). PostgreSQL errors show only "db error" unless `as_db_error()` is used; the runner's error text must come through it.
- **FR-012**: Crate layout (D28), see "Crate layout" below. The spike's prototype code lives under `rust/spikes/dbrun/`; production code, only after the owner signs a non-S verdict, goes to the `ai-gent-dbrun` crate. `ai-gent-core` never depends on a database driver.

### Must not regress

1. **Classification** (`classify`, lines 478-535): local only when proven (a compose project in this repository for containers; sqlite files inside the repository and not symlinks); everything else is production, staging or development with `writable: false`. Tests: `ProfilesTest::test_declared_local_without_proof_is_production`, `SqliteEndToEndTest::test_remote_refusals`, `::test_remote_read_is_read_only_even_past_the_classifier`.
2. **Statement scanning** (`scan`, `split_statements`, `classify_statement`, `is_ddl`, `catalog_only`, lines 568-720): reads versus writes, `EXPLAIN` forms, comments and quoting per engine, the MySQL backslash trick, SQL Server brackets, multi-statement splitting. Tests: all of `ClassifierTest` (reads, writes, engine_specific, system_databases_refused_for_writes, explain_forms, split, backslash_trick_refused, ddl).
3. **Cost rules** (`cost_rules`): `SELECT *` and unfiltered counts on user tables refused on remote targets unless `--allow-full-count`; catalog and local exempt. Tests: `CostTest`.
4. **Masking** (`mask_value`, `mask_free_text`, `mask_result`, `luhn`, `keep_last`): column-name rules, Luhn-checked card numbers, `--reveal` keeps secrets redacted. Tests: `MaskTest`.
5. **Redaction** of host, user and password in any error or log. Tests: `RedactTest`, `ProfilesTest::test_errors_are_redacted`, `::test_listing_never_shows_secrets`.
6. **Command log written before a statement runs** (`log_start`, `log_result`), plans with a tamper check (`test_tampered_plan_refused`), backups taken by `apply` before writing, row cap, timeouts, `script` never executing. Tests: `SqliteEndToEndTest` (8).
7. **Secrets**: pass first, `pass:<entry>` references, family entries, `secrets migrate`; profiles from the config directory; credentials only on the driver's stdin. Tests: `PassTest`, `TomlTest`, `MigrateAllTest`.
8. **Guards**: `plugins/db/hooks/guard.sh` and `opencode/guard/rules.mjs` (lines 147-218: only dbrun reads credential files; direct client calls with write SQL are denied or asked), `scripts/test-db-guard.sh` (4 mentions of `dbrun.py`), `scripts/test-secrets-guard.sh` (1), `opencode/guard/test/rules.test.mjs` (5). If the command word changes (`ai-gent db`), the patterns change with it in the same release; if it stays, they do not.

## Success Criteria *(mandatory)*

- **SC-001**: `decision.md` exists, follows the template, covers all six engines and E1-E8, and carries the owner's sign-off or an explicit "pending".
- **SC-002**: E1 passes: the 16 classifier, cost, mask, redact and network tests (and the engine-specific scan cases) are green as shared fixtures on a Rust core library, and the committed `golden.json` (reason text included) matches with the two lookaround gaps recorded.
- **SC-003**: For every engine marked "native" or "container" in the verdict, a prototype ran the engines script's checks for that engine and passed (including a server-side write refusal, FR-011), or the verdict marks the engine "unproven". The "not run" list (Oracle; plan, apply and restore; the remote-declared checks; PostgreSQL and MySQL TLS; musl; aarch64; Windows) is carried into `decision.md` until each item has a result.
- **SC-004**: The verdict states the user-visible requirement after the change in one sentence ("needs nothing", "needs Podman or Docker for SQL Server and Oracle", "needs uv") and lists the doc pages that say otherwise.
- **SC-005**: The size cost is measured: release binary size with and without the chosen drivers (a number, not an estimate; the report's figures are the starting table), and the build-toolchain cost is recorded (aws-lc-rs versus ring, a C compiler for bundled sqlite, musl, aarch64, Windows), because that, not size, is the constraint.
- **SC-006**: No file under `plugins/db/` changes during the spike.

## Edge Cases

- Oracle thin versus thick mode: Python `oracledb` is thin by default (no client libraries). The Rust `oracle` crate wraps ODPI-C and needs Oracle Client libraries 11.2+ on every user's machine, which the package cannot ship [RESEARCHED: S8]; the pure-Rust `oracledb` crate is a beta (26.0.0-beta.5) whose legacy 10G verifier support and TLS are unknown [RESEARCHED: S9]. E6a and E6b test them.
- SQL Server TLS: older servers negotiate TLS 1.0-1.2; some pure-Rust TLS stacks refuse legacy settings. E5 uses the `mssql/server:2022-latest` image and notes the encryption mode; the prototype needed `trust_cert` for that image's self-signed certificate, which is acceptable for the throwaway test and must not become a default.
- MariaDB versus MySQL timeouts: `max_statement_time` (MariaDB) versus `max_execution_time` (MySQL) are set per session after `SELECT VERSION()`; any new client must do the same.
- Read-only enforcement is per engine in the Python (`default_transaction_read_only=on` for PostgreSQL, read-only transactions elsewhere); each prototype must prove a write is refused by the server, not only by the scanner (`test_remote_read_is_read_only_even_past_the_classifier`).
- Windows: containers need Docker Desktop or a Podman machine; the client container joining another container's network namespace (`network_args`) has Linux semantics; E7 tests it or marks it not run.
- The pinned client image digest and driver pins are security-relevant (credentials go to them); any new pin follows the same "bump only after the engines script passes" rule.

## Out of Scope

- Implementing the port (its production tasks are Phase 5 of `tasks.md`, conditional on the owner's verdict); changing any skill, reference or guard; removing `uv` from other tools; a TUI; new engines; a connection pool; async execution.
- Keeping Python alive "just for db" as a silent fallback: if the answer is S, the requirement is stated openly in the db plugin docs and `ai-gent doctor`, not hidden.

## Open Questions

1. **Is "db needs uv (or a container engine)" acceptable in 3.0.0?** D19 says last or never. Recommended: yes for 3.0.0; revisit after the spike. It is the honest state today.
2. **Command word if db moves**: `ai-gent db` (D9 says "later `db`"). Recommended: yes, one binary; the guard patterns change in the same release.
3. **H-exec as the default hypothesis (updated from plain H).** The report recommends the safe first step: the Rust binary with the safety core and CLI, driving the Python `_exec` helper for every driver (phase 1), then native sqlite, PostgreSQL and MySQL/MariaDB (one client handles both families; the MariaDB run used the same binary), then SQL Server if `tiberius-ng` or another crate passes the engines script and the TLS checks, with Oracle staying on the helper until `oracledb` leaves beta. Plain H (a container client for SQL Server and Oracle) remains an option; the `sqlcmd` image route is assumed heavy and untested [RESEARCHED: S8, S9; the container routes are ASSUMPTION].
4. **Who runs E7 and E8** (Windows and aarch64 container behaviour)? Needs the owner's machines.
5. **Engines script ownership**: keep `scripts/test-dbrun-engines.py` as the acceptance harness after a port (Python stays a dev-only tool per D16), pointed at the new binary. Recommended: yes.

6. **Does `ai-gent-dbrun` depend on `ai-gent-core`?** Recommended: yes, only for the shared `--json` envelope, exit codes and paths, which keeps one set of conventions; the cost is that a core breaking change forces a dbrun release. The owner decides before the Connector trait task.
7. **Who configures Trusted Publishing for `ai-gent-dbrun`, and when?** The owner (crates.io settings, same environment as the other crates). Recommended: before the first real publish of the crate, which is not before the port ships (3.x).

## Crate layout (D28)

Applies to the production port that follows a non-S verdict; the spike itself stays in `rust/spikes/dbrun/`.

- `ai-gent-core` stays lean and must not depend on any database driver.
- A new library crate **`ai-gent-dbrun`** (`rust/crates/ai-gent-dbrun/`; the name is reserved and published as 0.1.0 on crates.io on 2026-11-01 [OBSERVED: the crates.io API shows 0.1.0, created that day]) holds: the safety core (scanner, splitter, classifier, cost rules, masking, redaction, plan engine, logging), a `Connector` trait, and one module per engine behind Cargo features `sqlite`, `postgres`, `mysql`, `mssql`, `oracle`. A **process connector** drives the Python `_exec` helper through its JSON contract (a request on stdin, one JSON line on stdout); it is how option H-exec keeps Oracle, and SQL Server until a native driver proves itself.
- The `ai-gent` binary depends on `ai-gent-dbrun` with default features chosen per target (for example no `oracle` on Windows).
- One crate per connector is **not** published in 3.0.0. A connector moves to its own crate only when (a) it needs a different release cadence or licence, (b) an outside user wants it alone, or (c) its dependency tree makes the shared crate hard to build. A fork-dependent `mssql` or the `oracle` connector is the likeliest first split, after the trait has been exercised by at least two native connectors.
- The `ai-gent-dbrun` README says it is built for ai-gent's own policy and is **not a general SQL validator**: `sqlparser` was measured as unsafe for classification (163 of 1026 disagreements, 119 where the parser says READ and dbrun says WRITE).
- Versions: independent SemVer like `ai-gent-core` (0.x until its API is deliberately stable, D23). Publish order: `ai-gent-core`, then `ai-gent-dbrun`, then `ai-gent`. Trusted Publishing for `ai-gent-dbrun` (repository `lucasvmigotto/ai-gent`, workflow `release.yml`, environment `crate-release`) is for the owner to set up; until then it is not configured [not verified here].
- Dependency direction: `ai-gent-dbrun` may use `ai-gent-core` for the output envelope, exit codes and paths; the reverse never (Open Question 6).
